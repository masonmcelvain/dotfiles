# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A chezmoi-managed dotfiles repository for two machines: `masons-xps` (Ubuntu desktop) and a Mac laptop. The chezmoi source directory is the repo root; there is no `.chezmoiroot`.

## Chezmoi Commands

```bash
chezmoi apply              # Apply all changes to home directory
chezmoi apply ~/.bashrc    # Apply a single target file
chezmoi diff               # Preview changes before applying
chezmoi edit ~/.bashrc     # Edit the source file for a target
chezmoi cd                 # cd into this source directory
```

## Linting

`.mise.toml` pins shellcheck, chezmoi, go and staticcheck as dev tools for this repo. Run `mise run lint` after a change; it runs every task in `.mise/tasks/lint/`, and `mise run lint:shell` or `mise run lint:go` runs just one. Run `mise run test` (`.mise/tasks/test`) after changing Go. CI runs the same tasks: `.github/workflows/shell.yml` on every push and PR, and `.github/workflows/go.yml`, with lint and test as separate jobs, on every PR but only on pushes that change `mm/` or its tasks. A `main` ruleset requires `shellcheck`, `lint` and `test` with admins bypassing it so direct pushes still land; a required check that never reports blocks a PR forever, which is why `go.yml` runs on every PR. `.github/dependabot.yml` opens a weekly PR bumping the workflows' actions, and `.github/workflows/dependabot-merge.yml` turns on GitHub's auto-merge for it when it only touches workflows; the `.mise.toml` pins and mm's Go modules are bumped by hand. mise only activates in interactive shells, so from a non-interactive one call `~/.local/bin/mise run lint`, or `mise install` first on a fresh checkout.

Plain scripts are found by shebang. Shell templates (`dot_bash*`, `*.sh.tmpl`, or a shebang on line 1) are rendered with `chezmoi execute-template --override-data` for each host in the task (`masons-xps` on linux and `mac` on darwin) and checked as `<file>@<host>`. Line numbers in those findings are the rendered file's, not the template's; find the line by its text. `lint:go` runs `gofmt -l`, `go vet` and `staticcheck` over `mm/`, reporting all three even when one fails. It runs `go vet` and `staticcheck` once with `GOOS=linux` and once with `GOOS=darwin`, since `internal/zellij` reads processes differently on each, so either host checks both; `mise run test` only tests the host's own.

## Chezmoi Naming Conventions

Files use chezmoi's source-state naming:

- `dot_` prefix -> dotfile (e.g., `dot_bashrc.tmpl` -> `~/.bashrc`)
- `private_` prefix -> restricted permissions (e.g., `private_dot_config/` -> `~/.config/`)
- `executable_` prefix -> executable permission
- `.tmpl` suffix -> Go template, rendered at apply time

## Templating

Templates use Go's `text/template` syntax with chezmoi data. Branch on `.chezmoi.os` (`darwin` or `linux`) for the Mac, since its hostname isn't fixed, and on `.chezmoi.hostname` for things tied to `masons-xps` itself:

```
{{ if eq .chezmoi.os "darwin" -}}
# Mac-specific
{{- end }}
{{ if eq .chezmoi.hostname "masons-xps" -}}
# Ubuntu-specific
{{- end }}
```

The Mac is an allowlist: on darwin, `.chezmoiignore` ignores everything and then un-ignores (`!`) only bash, git, gpg-agent, ssh (its config, whose `UseKeychain` only macOS understands), helix, zellij, alacritty, starship, skhd, Claude Code, mm (through `build-mm.sh`) and the few `~/.local/bin` scripts they call (hx-open among them, which needs GNU grep's `-P`, so the Mac's `.bashrc` puts Homebrew's GNU grep `gnubin` first on PATH), so a new file reaches only Linux unless it's added there. A directory has to be un-ignored before anything inside it can be. `chezmoi managed --override-data '{"chezmoi":{"os":"darwin"}}'` lists what the Mac gets. The Mac's terminals start login shells, so it also gets `dot_bash_profile`, which only sources `~/.bashrc`; on Linux it's ignored so it doesn't shadow `~/.profile`. Mac-only setup lives in darwin blocks: Homebrew's `shellenv` and GNU grep's `gnubin` first in `.bashrc`, Alacritty's `option_as_alt` (so zellij's and helix's Alt bindings work unchanged) and a fixed theme import, zellij's `pbcopy`, `gpg` instead of `gpg2`, git pushing over HTTPS with `gh auth git-credential` (so `gh auth login` should decline to set up git itself, which would write to the chezmoi-managed `~/.gitconfig`), and `~/.gnupg/gpg-agent.conf` pointing at `pinentry-mac` (from Homebrew), so commits can be signed from shells with no terminal. The Mac doesn't get `~/.fonts`, since macOS reads `~/Library/Fonts` and not fontconfig: `run_onchange_install-mac-fonts.sh.tmpl` copies only Liga SF Mono Nerd Font there, and Alacritty's config names it in a darwin block, because Linux reaches it through fontconfig's `monospace` alias and without it starship's Nerd Font glyphs don't render. `run_onchange_after_configure-mac-screencapture.sh.tmpl` saves screenshots to `~/Pictures/screenshots` and loads `~/Library/LaunchAgents/local.move-screencasts.plist`, a launchd agent that moves screen recordings on to `~/Movies/screencasts`, since macOS saves both to the one `com.apple.screencapture location`

The repo is public, so nothing from my employer, Nordic Naturals, goes in it beyond what the tooling needs to recognize their repos (the `nordicnaturals` Bitbucket workspace and Jira site). No real issue keys, commit messages, PR numbers, repo names, product names, URLs, code or details of their stack, not even as examples in skills, docs, tests or commit messages; make examples up (`US-1234`, `acme/storefront`).

Custom data variables live in `~/.config/chezmoi/chezmoi.toml`, which is *not* in this repo — the repo is public, so secrets belong there:

- `.gitconfig.email`, `.gitconfig.signingkey`
- `.gitconfig.bitbucketEmail` (optional): the address commits to Bitbucket remotes use, which the signing key also carries as a UID; without it a host gets no Bitbucket identity

## Architecture

- **Shell**: `dot_bashrc.tmpl`, `dot_bash_aliases.tmpl` - hostname-conditional shell setup with fnm, zoxide, starship, and fzf's CTRL-R history search (its CTRL-T and ALT-C bindings are turned off)
- **Git**: `dot_gitconfig.tmpl`, `dot_gitmessage` - templated for the GPG key and email
- **Editors**: `private_dot_config/helix/` (primary editor), `dot_vimrc.tmpl` (fallback)
- **Terminals**: `private_dot_config/alacritty/` (emulator, made the GNOME default by `private_dot_config/xdg-terminals.list`, which `xdg-terminal-exec` reads; masons-xps only), `private_dot_config/zellij/` (multiplexer), `dot_tmux.conf.tmpl` (alt multiplexer)
- **GNOME extensions**: `private_dot_local/private_share/private_gnome-shell/extensions/` (masons-xps only, via `.chezmoiignore`). `spotify-fullscreen@masons-xps` fullscreens Spotify when it opens, because Spotify ignores `--start-fullscreen`. `hide-date-menu-cards@masons-xps` hides the Today and World Clocks cards in the clock dropdown, because GNOME has no setting for them; it re-hides them whenever the shell re-shows them. Enabling either is a `gsettings` change to `org.gnome.shell enabled-extensions`, not a file, and on Wayland the shell only picks up a new or edited extension at the next login
- **Open paths on screen**: `Alt o` (zellij) opens the file paths visible in the focused pane in helix, in a floating pane that starts fullscreen (`Alt z` shrinks it), via `private_dot_local/bin/executable_hx-open`. The keybind runs `DumpScreen` before `Run`, because once the floating pane opens it has focus and zellij can't say which floating pane had it. One path opens directly with any `:line:col`; several are listed in helix's file picker by opening `hx` on a temp directory of symlinks mirroring their absolute paths, with a `-c` copy of the user config that turns off the picker's hidden and gitignore filters (helix 25.07 ignores a workspace `config.toml`)
- **Global hotkeys**: `private_dot_config/skhd/skhdrc` (Mac only) binds Cmd+A, in every app, to a new Alacritty window, opened through the newest instance's IPC socket (`Alacritty-<pid>.sock` in `getconf DARWIN_USER_TEMP_DIR`, where an Alacritty started by `open` creates it) so they share one process. Cmd+Up fills the screen with the focused window, without a full-screen Space, and Cmd+Down shrinks it back, through `private_dot_local/bin/executable_window-size` (JXA resizing over the Accessibility API, since only apps with a Window menu have macOS's own Fill, and Alacritty has none). skhd runs as a launchd service (`skhd --start-service`, plus Accessibility access) and hotloads the config on apply; the `skhd` skill covers its syntax and debugging
- **Fonts**: `dot_fonts/` - SF Mono, SF Pro, Liga SF Mono Nerd Font, Apple Color Emoji
- **Scripts**: `bin/executable_vnstat_graph.sh`, `private_dot_local/bin/executable_hx-theme.sh` and `private_dot_local/bin/executable_debug-touchpad` (masons-xps only). `debug-touchpad`, run while the touchpad is dead, records it at each layer (its interrupt count, raw evdev, libinput's reading, GNOME's settings) to `~/touchpad-debug/`, and says which layer lost the touches or clicks
- **mm**: `mm/` is a Go module (Bubble Tea v2) building one binary with a subcommand per tool: `mm agents`, `mm sessions`, `mm ship` and `mm agent-status`. It isn't a chezmoi target (`.chezmoiignore` skips it); `run_onchange_before_build-mm.sh.tmpl` runs `go build` into `~/.local/bin/mm` whenever a hash of the Go source changes, so the host needs Go installed. It runs as a `before_` script so the binary exists before `modify_settings.json` points the hooks at it. `.chezmoiremove` deletes the shell scripts it replaced. It builds on both hosts, so the Mac gets it (`.chezmoiignore` un-ignores `build-mm.sh`) along with the zellij bindings and aliases that open it; the only platform split is how `internal/zellij` finds pane ttys (`input_linux.go` walks `/proc`, `input_darwin.go` runs `ps`) and where zellij's cache lives (`~/Library/Caches/org.Zellij-Contributors.Zellij` on macOS). `internal/picker` is the full-screen list TUI behind both pickers - refresh tick, keys (1-9, wrapping j/k, g/G, enter, r, ctrl-l, q or esc) and detail pane; a picker supplies a `picker.Source` whose `Open`/`Key` return a `picker.Action` (flash, reload, quit, exec a command, ask a one-key question, or read a line). With stdout not a terminal, both pickers print a plain table
- **Session picker**: `mm sessions` (`mm/internal/sessions`) - a picker over zellij sessions listing each one's git branch and directory, so a session is recognizable by the work in it rather than by its name alone. `zf` (bash) and `Alt f` (zellij, a floating pane) both open it; it attaches from a plain shell and `switch-session`s from inside one, and either path resurrects an exited session. `d` deletes the selected session after a `y` confirmation, killing it first if it's live (`zellij delete-session --force`), then detaches HEAD in its checkout so another worktree can check out the branch. It skips this when the tree is dirty or another live session shares the checkout. `b` (or `mm sessions branch NAME`, aliased to `zb`) prompts for a branch and goes to the session that has it checked out, live ones first; if none does, it's an error. Session cwds are read from zellij's own cache (`~/.cache/zellij/*/session_info/<name>/session-layout.kdl`, or its macOS equivalent) rather than from `zellij action dump-layout`, which needs a running server per session and hangs on exited ones; branches come straight out of `.git/HEAD`, since a `git` per session is what would make it feel slow. Both groups list most recently used first, and the age column says how long ago: for a live session, its panes' newest pty atime (the last keystroke, the clock `w` uses for IDLE), found by walking `/proc` (or `ps` on macOS) for the zellij server's children; a session renamed after it started keeps its old name on the server's command line, so it gets no pty age; for an exited one, the mtime of its `session-metadata.kdl`, which zellij stops rewriting when it exits
- **Ship** (Mac only: `mm ship` refuses to run elsewhere, and `.chezmoiignore` keeps the skill and its agents off Linux): hand a Jira issue, a Bitbucket PR, or a task in words to an agent and come back to a battle-tested branch that waits for my go-ahead before anything leaves the machine. `mm ship TARGET` (`mm/internal/ship`), run from any checkout of a Bitbucket repo, takes an issue key (`US-1234`) or Jira link, a PR number or link, or words; after an issue or PR, the remaining arguments are a note (`mm ship US-1234 "verify it's a problem first"`) that ends the agent's prompt as an instruction from me, which the skill keeps in the ledger. Anything with a space in it parses as a task, so a link with words after it is never read as the link alone. It prepares a branch (the issue key, `ship/<slug>` for a task, or the PR's own, picking up an existing local or origin branch of that name) in a git worktree under `.claude/worktrees/` (globally ignored by `private_dot_config/git/ignore`), switching a clean worktree already at that path onto the branch in place, as `mm sessions`' `d` leaves one on a detached HEAD, and a zellij session named `<repo>-<key>` (or `-pr<n>`, `-<slug>`) for it, then starts `claude --permission-mode auto` in the session's claude tab, through an interactive shell so mise and fnm set up PATH, and leaves it in the background. A PR's branch comes from `bkt pr view --json`, and origin's default branch from `origin/HEAD` or else `bkt api`. Claude is told to "use the ship skill" rather than given `/ship`, because Claude Code leaves a command-line prompt that starts with a slash unsent. The pane is replaced with `zellij action new-pane --in-place --pane-id`, because typing into a background session with no client attached doesn't land. Created sessions drop the launching agent's `CLAUDE*` variables, which would otherwise mark every Claude in them as that agent's child. The skill (`dot_claude/skills/ship/`) makes the main agent a chief of staff that delegates rather than writes code: it reads the issue with `acli`, specs the work with acceptance criteria, a QA plan and deploy notes before any code exists, has `builder` agents implement it (it does the committing), runs a review board (`review-correctness` always, plus `review-security`/`-frontend`/`-data`/`-ops` as the diff warrants) whose serious findings a `finding-verifier` tries to refute before the builder fixes them, and has a `qa-engineer` run the QA plan, all locally, driving the browser with a headless `agent-browser` session per branch and falling back to my own Chrome through Claude in Chrome when a bot check blocks it, with production read-only and mutations only on local dev and dev stores. It then drafts the PR title and description (changeset, QA steps taken, deploy steps) and gathers screenshots into `~/Pictures/screenshots/<key>/`, next to the Mac's own screenshots, notifies me, and waits. Only my reply in the session approves a push; anything else I say is feedback it fixes before asking again. On go it pushes, opens the PR with `bkt pr create --with-default-reviewers` (Bitbucket only adds default reviewers to PRs made in its web UI), and opens the screenshots folder and PR for me, since Bitbucket's API can't attach files. Board and QA results never go on the PR. A 20-minute aftercare cron then watches pipelines, conflicts and comments, fixes and commits locally, and asks for a go-ahead per push; it never replies to or resolves comments, and stops once the PR merges or settles. Its state lives in `$(git rev-parse --git-dir)/ship/ledger.md`, so `mm ship` on the same target resumes it. It never merges, approves or marks a PR ready, or changes Jira. Each run appends a retro to `~/.claude/ship-retros.md`
- **Nordic conventions**: `dot_claude/skills/nordic/` (Mac only, via `.chezmoiignore`) holds Nordic Naturals' branch, commit and PR rules: the Jira key is the branch name and leads every commit subject and PR title (`US-1234 fix: ...`), and PR descriptions carry the Jira link, changes, QA and a Deploy section. It applies by origin (the `nordicnaturals` Bitbucket workspace) rather than by path, since `~/code/` may hold other repos too. A darwin block in the global `dot_claude/CLAUDE.md.tmpl` tells Claude to load it before branching, committing or opening a PR, so it's not left to the skill's description to trigger
- **Agents picker**: `mm agents` (`mm/internal/agents`; `Alt a`, aliased to `ag`) lists the agents `mm agent-status` recorded and jumps to one's zellij tab, attaching or switching sessions as needed; `d` dismisses one
- **Notifications**: `private_dot_local/bin/executable_notify` sends a desktop notification, through `osascript` on macOS (only the title and body; macOS attributes it to Script Editor, which needs notifications allowed once). Its two callers are `executable_yo` (`yo <slow command>` notifies when the command finishes, and adds a terminal bell that zellij turns into a `[!]` tab flag) and the Claude Code hooks
- **Notification stacking**: `private_dot_local/bin/executable_notify-relay` sends notifications from one long-lived process, because GNOME stacks a notification center group per sender pid and app name, and every `notify-send` is a new pid. `notify` tries it first and falls back to `notify-send`. It runs from `private_dot_config/systemd/user/notify-relay.socket` (masons-xps only, via `ConditionHost`), which has to be enabled once with `systemctl --user enable --now notify-relay.socket`. It deliberately sends no `desktop-entry` hint: that groups by app instead, but GNOME destroys an app's notifications as soon as the sender leaves the bus
- **Claude Code config**: `dot_claude/` - global CLAUDE.md, keybindings, custom agents (the ship roster), skills and commands
- **Local review loop**: review a diff without leaving the terminal - `hkg`/`hkr` (bash) open the working tree or the branch's own work in [hunk](https://www.hunk.dev/), `c` (hunk) leaves an inline comment on the selected hunk, and the `/resolve` command (`dot_claude/commands/resolve.md`) has Claude read them back over `hunk session comment list --type user`, fix or push back on each, and clear them. `hkr` diffs from the merge base rather than the branch tip, so upstream drift stays out of the changeset; `hxr`/`hxg` are the helix counterparts, for editing the same files rather than reviewing them. The comments live in the running TUI, not the tree - close it and they're gone
- **Reviewing peers' PRs**: `/review-pr <PR>` (`dot_claude/skills/review-pr/SKILL.md`) makes Claude a review assistant rather than the reviewer - the call on a change is mine, and it judges intent rather than every line. It checks the PR out in the current checkout (stopping if the tree is dirty), briefs me on intent, unmentioned changes, what's hard to reverse and where the risk is, then answers my questions with `file:line` evidence while keeping a "still to decide" checklist and ending every reply with a status line, so a tangent doesn't lose the review. Findings go in only when I say so, into `~/reviews/<owner>-<repo>-<n>.md`, which I edit freely: everything above its bare `---` is posted, the notes below it never are. Posting re-reads the file, folds comments on lines outside the diff into the body, and submits it with the verdict as the event ("post it" is the go-ahead, with no confirmation round in chat; a pending review only when I ask for one); it then moves what it posted below the line so the next round starts empty
- **Jira and Bitbucket**: work uses Jira Cloud and Bitbucket Cloud on the Mac. Agents drive them through Atlassian's `acli` (`brew install atlassian/acli/acli`, after `brew trust atlassian/acli`) and the community `bkt` (`brew install bitbucket-cli`), both installed by hand and logged in once with `acli jira auth login --web` and `bkt auth login https://bitbucket.org --kind cloud --web`. Tokens live in the macOS keychain, not here. The `jira` skill (`dot_claude/skills/jira/`) is hand-written; `bkt`'s comes from `.chezmoiexternal.toml.tmpl`, which fetches the repo archive at the tag matching `bkt --version`, so the skill's command reference moves with each `brew upgrade` (Homebrew's build doesn't ship it). Both are skipped on a host without the CLI
- **Hunk config**: `private_dot_config/hunk/config.toml` - theme, `watch`, and the keybinding for the bundled review skill. `dot_claude/skills/symlink_hunk-review.tmpl` resolves that skill's path at apply time (it sits inside the fnm node install, so the path moves on every node upgrade) and `.chezmoiignore` skips it on a host without hunk, since the `output` call would otherwise fail the apply
- **Agent status**: `mm agent-status` (`mm/internal/agents/hook.go`) - Claude Code hook handler that writes agent state to `~/.cache/agents/<session_id>.json` and renames the agent's zellij tab (`- name` working, `○` idle: done or needing input). At the end of a turn it starts `mm agent-status name` in the background, which asks Haiku (a bare `claude -p` with hooks off) for a label from the prompts, the agent's last reply, the branch's PR and the sibling tab names, because Claude Code's own title only sees the first prompt ("review this pr" becomes "PR review"). It re-runs when that title changes; a `claude -n` name beats the label, which beats the title
- **Claude hooks**: `dot_claude/modify_settings.json` (a chezmoi modify script) merges the `mm agent-status` and `notify` hook registrations into `~/.claude/settings.json`; the rest of that file stays unmanaged because Claude Code live-edits it. Both hook commands are identical on every machine, so no host templating is needed; the `mm agent-status` hooks are only registered where `~/.local/bin/mm` exists, so a host without Go gets just the `notify` ones. The script also removes the hooks it owns before re-adding them, which migrates any hand-written `notify-send` hooks, and the old `agent-status.sh` one, in place
